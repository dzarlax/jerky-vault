Frontend Plan: Backend Ingredient Unit Contract

Task Summary

Update the web/admin frontend so price and recipe unit choices come from the backend workspace ingredient contract: unit_profile, default_unit, and allowed_units. The web UI should stop treating local ingredient type metadata as the primary source of unit truth while retaining a temporary fallback for staged rollout safety.

Backend Evidence

  • jerky-vault-back/models/workspace_ingredient.go now exposes transient response fields unit_profile, default_unit, and allowed_units.
  • jerky-vault-back/constants/unit_profiles.go maps workspace category first, then ingredient type, into profiles mass, fine_mass, volume, count, and time.
  • Canonical backend defaults are kg for mass, g for fine mass, ml for volume, pcs for count, and hh for time.
  • Allowed backend units are ["kg", "g"], ["g", "kg"], ["ml", "l"], ["pcs"], and ["hh"], depending on profile.
  • The backend deliberately keeps price and recipe writes permissive in this pass. Frontend should guide users with allowed_units but not assume strict server-side validation has landed.
  • Swagger has been regenerated in the backend for the additive workspace ingredient fields.

Current Frontend Behavior

  • src/types/api.ts does not type the new workspace ingredient unit fields.
  • src/utils/ingredientTypes.ts stores local unit arrays on type metadata and exports getUnitsForIngredientType.
  • src/pages/prices.tsx fetches /api/workspace-ingredients, but flattens the rows to nested Ingredient[] before opening AddPriceModal.
  • AddPriceModal uses getUnitsForIngredientType(selectedIngredient.type) and picks the first local unit as default.
  • src/pages/recipes.tsx also fetches workspace ingredients and flattens them to Ingredient[] before passing data into create/edit recipe modals.
  • CreateRecipeModal and EditRecipeModal also derive unit dropdown options from the local ingredient type helper.
  • Locale files already include kg, g, ml, pcs, and hh. A current static search did not show l, so implementation should add it to all locale files if still missing.

Desired Behavior

  • Price and recipe forms receive the full WorkspaceIngredient object when they need unit choices.
  • If allowed_units is non-empty, the dropdown uses it exactly in backend order.
  • If default_unit is present and exists in allowed_units, the dropdown defaults to that unit.
  • If backend unit fields are missing, empty, or malformed, the UI falls back to the existing local getUnitsForIngredientType behavior.
  • Existing saved recipe rows and price table rows continue rendering their stored unit values, including legacy/custom values.
  • Ingredient type metadata remains available for labels, icons, filters, and badges. Unit arrays can stay temporarily as fallback until backend rollout is complete.

Assumptions

  • The active ingredient source for price and recipe creation remains GET /api/workspace-ingredients, not global GET /api/ingredients.
  • The backend contract is additive and deployed independently, so the frontend must tolerate old responses during local/dev/prod skew.
  • The request payloads for prices and recipe ingredients remain unchanged: ingredient_id, quantity, and unit.
  • No UI for editing unit profiles or overrides is part of this pass.
  • No separate local Next.js dev server should be started for QA in this repo; use the existing dev compose environment if browser verification is needed.

Likely File Changes

  • src/types/api.ts: add UnitProfile and optional unit_profile, default_unit, allowed_units fields to WorkspaceIngredient.
  • src/utils/ingredientTypes.ts: keep current unit arrays as fallback and optionally add a small helper for fallback unit resolution only.
  • New or existing helper under src/utils/: centralize workspace unit option resolution so price and recipe modals do not duplicate fallback rules.
  • src/pages/prices.tsx: pass workspaceIngredients into AddPriceModal instead of flattened ingredients for unit-sensitive behavior.
  • src/components/modal/Prices/AddPriceModal.tsx: select unit options from the selected workspace ingredient contract and default to default_unit.
  • src/pages/recipes.tsx: pass workspace ingredients to create/edit recipe modals while preserving existing filter and display behavior.
  • src/components/modal/Recipe/CreateRecipeModal.tsx: use backend unit contract for new recipe ingredient rows.
  • src/components/modal/Recipe/EditRecipeModal.tsx: use backend unit contract when adding an ingredient to an existing recipe.
  • locales/en/common.json, locales/ru/common.json, locales/rs/common.json: add l if still missing.

Implementation Steps

  1. Type the backend response in src/types/api.ts, keeping the new fields optional.
  2. Add a shared unit resolution helper that accepts a WorkspaceIngredient and returns ordered unit options plus the default selected unit.
  3. Make the helper validate basic shape: non-empty string units only, no duplicate units, and use backend values only when at least one valid unit exists.
  4. Keep fallback to getUnitsForIngredientType(workspaceIngredient.ingredient.type) for missing old backend responses.
  5. Update price page data flow so AddPriceModal receives workspace ingredient rows and maps labels from workspaceIngredient.alias || ingredient.name if useful.
  6. Update AddPriceModal selection, unit option calculation, and reset behavior around the selected workspace ingredient.
  7. Update recipe page data flow so create/edit modals receive workspace ingredient rows for unit decisions, while filters can continue using flattened ingredient options.
  8. Update recipe create/edit unit dropdowns to use the shared helper and preserve the existing duplicate-ingredient and quantity validations.
  9. Add missing l locale label in all supported languages if not already present at implementation time.
  10. Run static search to confirm no unit-sensitive price or recipe form still uses getUnitsForIngredientType as the primary source when workspace contract fields are available.

Risks

  • Passing flattened Ingredient[] into modals would silently discard backend unit metadata and make the change look complete while still using local mapping.
  • Backend category has priority over ingredient type, so frontend should not recompute the profile from type when backend fields are present.
  • The unit l may render as the raw key until locale entries are added.
  • Strict client-only validation could reject legacy/custom unit data that the backend still intentionally accepts. This pass should guide new entries, not rewrite history.
  • Manual auth/workspace headers still exist in some recipe/price paths. This plan should avoid broad request plumbing refactors unless necessary for the unit contract.

Rollback Plan

  • Revert the frontend changes to modal props and unit helper usage.
  • Keep backend additive fields in place because old frontend code ignores unknown response fields.
  • If a partial rollback is needed, leave the type additions and locale key in place and restore local unit selection in the three affected modals.

Open Questions

  • Should ingredient labels in the modals show workspace aliases when present, or keep global ingredient names for now?
  • Should the UI expose the backend unit profile label anywhere, or keep it purely internal to dropdown choices?
  • Should the fallback local unit arrays be removed immediately after frontend and backend deploy, or kept through one release cycle for older environments?
