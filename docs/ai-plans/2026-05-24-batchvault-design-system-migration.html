Implementation Plan: BatchVault Design System Migration

Approval required before implementation

Created 2026-05-24 from D:\Projects\Code\Personal\jerky-vault. This plan covers planning and implementation for applying the local dzarlax design system to the BatchVault frontend without breaking the existing production build or dev-compose workflow.

Task Summary

Migrate BatchVault toward the shared dzarlax design system while preserving the product's operational dashboard ergonomics. The migration should reuse design-system tokens and suitable CSS primitives, avoid directly importing editorial website patterns, and identify reusable app-specific components that can later be upstreamed into the design system.

Inspected Current State

BatchVault frontend

  • Next.js 14 Pages Router in src/pages.
  • React Bootstrap and Bootstrap 5.3 are active dependencies.
  • Global imports currently load bootstrap.min.css, src/styles/design-system.css, and src/styles/components.css from src/pages/_app.tsx.
  • The current local theme is the old Smoked Ember token set with burgundy brand colors, slate neutrals, and [data-theme="dark"].

Shared design system

  • CSS-first, minimal vanilla JS, no npm runtime dependency.
  • Sources are split across tokens, base, components, themes, brand, js, and generated dist.
  • Available component CSS includes buttons, forms, cards, tables, badges, alerts, spinner, empty-state, KPI/stat/tag chips, nav, lang switcher, theme toggle, and combobox.
  • The base design principles are currently website/editorial oriented: warm ivory background, dark graphite accent, Georgia headings, system body font, and [dark-mode] for dark mode.

Key Design Decision: Typography

The shared design system's base typography uses serif headings for h1, h2, and h3. That is appropriate for dzarlax.dev editorial pages, but it is not a good default for BatchVault's dense operational UI.

Decision proposed for approval: do not import base/typography.css directly into BatchVault. Instead, use design-system size and line-height tokens where helpful, but introduce a BatchVault application typography adapter with system sans headings, tighter table/form density, and zero or near-zero letter spacing.

  • Body and headings: system sans stack.
  • Page headings: 600 or 700, compact line-height, no serif.
  • Tables and forms: optimized for scan speed and repeated use.
  • Marketing/editorial presets remain out of the app shell.

What We Should Not Reuse Directly

  • base/typography.css as-is, because serif editorial headings are not right for an operational SaaS/admin interface.
  • hero.css, prose.css, share.css, footer.css, and most of timeline.css, because they are content-site patterns rather than BatchVault workflow UI.
  • Design-system brand assets from brand/, because BatchVault now has its own product brand and logo.
  • Vanilla JS modules from js/ directly in app flows. BatchVault should keep navigation, combobox, and interaction state in React components.
  • The generated dist/dzarlax.css as a blind import before testing, because it can override Bootstrap and current app-specific styles in unpredictable places.

Proposed Implementation Steps

  1. Create a small local visual inventory: current dashboard, orders table, product cards, modal form, sign-in page, mobile sidebar, dark mode.
  2. Define the BatchVault design adapter: product accent, neutral surfaces, typography preset, density, radius, shadows, and dark-mode bridge.
  3. Introduce the adapter with minimal import churn and verify Bootstrap still renders correctly.
  4. Refresh foundational app shell components first: Sidebar, Header/mobile toggle, theme/language controls.
  5. Refresh reusable state and data components: MetricCard, StatusBadge, EmptyState, LoadingState, ErrorState, NotificationToast, SelectDropdown.
  6. Apply the refreshed patterns to one representative high-traffic page first, preferably dashboard or orders.
  7. Expand across remaining CRUD pages only after the representative page works in light, dark, desktop, and mobile.
  8. Document design-system gaps discovered during the migration and, if useful, prepare a separate PR for upstream design-system additions.

UX and Deployment Impact

  • UX impact is broad: most screens may receive visual changes, but API behavior, authentication, data fetching, and backend contracts should stay unchanged.
  • No database or backend migration is expected.
  • No production CDN dependency should be introduced. If shared design-system artifacts are consumed, they should be vendored, copied, or baked into the build artifact.
  • The existing dev-compose flow should remain intact: use the persistent frontend container to serve rebuilt output, and only run the builder after frontend source changes.

Risks and Edge Cases

  • Bootstrap and design-system class names may collide, especially generic names like .btn, .card, .badge, and table styles.
  • Typography can become too editorial if shared base styles are imported without an app preset.
  • Global reset changes can affect modal sizing, dropdown portals, chart containers, and Bootstrap layout utilities.
  • Dark-mode attribute mismatch between [data-theme="dark"] and [dark-mode] can silently break themes.
  • One-shot page restyling can leave inconsistent UI if reusable components are not migrated first.
  • The design-system dist output is generated; edits must happen in source files if we later upstream changes.

Rollback Plan

Keep the migration in a dedicated branch. If the approach causes broad visual regressions, revert the adapter import and touched component styles while leaving the plan document intact. If only individual components regress, roll back those components to the previous local styles and continue with a narrower token-only migration.

Open Questions

  • Should BatchVault keep its current burgundy/copper brand direction, or should it move closer to the design-system graphite/ivory defaults?
  • Should we eventually migrate BatchVault dark mode from [data-theme="dark"] to design-system [dark-mode], or keep a compatibility bridge permanently?
  • Should upstream design-system additions be a separate PR after BatchVault proves the patterns, or should we update both repos in parallel?
  • How far should this first branch go: token adapter only, app shell plus reusable components, or all visible CRUD pages?
