Implementation Plan: BatchVault Brand Rename Phase 1

Approval required before implementation

Created 2026-05-24 from D:\Projects\Code\Personal\jerky-vault. This plan is for a product-facing rename and positioning update only; infrastructure identifiers stay stable unless explicitly approved later.

Task Summary

Rename the user-visible product brand from JerkyVault / Jerky Vault to BatchVault and shift the product copy from jerky-only management to small food production / batch operations. Preserve technical identifiers such as repositories, package names, image names, domains, compose service names, database names, and existing deployment paths.

Rename Rationale

The old name anchors the platform to one product category. The actual system is broader: recipes, ingredients, production batches, products, clients, orders, pricing, cost, status tracking, margin, and dashboard workflows. The new name should keep a food-production feel without implying the product is only for jerky.

BatchVault keeps continuity with the old Vault identity while making the core domain broader: batches, recipes, orders, and production records for small food producers.

  • Browser-visible app chrome says BatchVault.
  • Document metadata describes BatchVault, not JerkyVault.
  • User-facing README and Docker guide introduce the product as BatchVault.
  • Backend docs refer to BatchVault Backend where this is product-facing documentation.

  • Feature copy should use broader terms like food production, batches, products, orders, ingredients, pricing, cost, and margin instead of jerky-specific framing.
  • Domain, image, compose service, repo, package, executable, and database identifiers remain unchanged for now.

Implementation Steps

  1. Wait for the current frontend hotfix/GHCR PR to settle or create a fresh branch from updated origin/main.
  2. In the frontend, update visible brand strings and metadata to BatchVault.
  3. In frontend docs, update product-facing names and descriptions while leaving repo/image/domain/service identifiers unchanged. Replace jerky-only positioning with small food production / batch operations copy.
  4. In backend, update product-facing docs and source annotations only. Avoid manual edits to generated Swagger output unless the repo's existing workflow expects committed generated docs.
  5. Run grep checks to ensure no unintended product-facing JerkyVault remains in active UI/docs, while expected technical identifiers remain.
  6. Run frontend and backend verification commands, then open PR(s). Prefer separate PRs per repo unless the user wants a coordinated multi-repo rollout.

Test Plan

  • Frontend: npm run lint and npm run build.
  • Frontend browser QA: load the app and confirm header/sidebar/footer/title/meta-visible behavior where applicable.
  • Backend: run the repo's Go checks after verifying the correct module path, likely go test ./... and go build ./....
  • Search checks: rg "JerkyVault|Jerky Vault|Jerky-vault" src README.md DOCKER.md in frontend and equivalent docs search in backend.
  • Copy check: rg "jerky production|jerky management|jerky recipes|jerky product" README.md DOCKER.md src should not find active product positioning unless it is intentionally describing legacy repo/domain/image names.
  • Ensure technical identifiers are not accidentally renamed by checking compose, workflow, image, and domain references.

Risks and Edge Cases

  • Blind replacing jerky would break real domains, package names, image names, DB names, and deploy paths.
  • Changing generated Swagger docs manually may create drift from source annotations.
  • Changing repo/package/image names in the same pass would require a broader CI/deploy migration and is deliberately avoided here.
  • Some old names should remain in historical plan files and rollback notes because they describe past states.

Rollback Plan

Rollback is a normal git revert of the brand rename commit(s). Because phase 1 avoids infrastructure identifiers, rollback should not require image, DNS, database, or deploy changes.
