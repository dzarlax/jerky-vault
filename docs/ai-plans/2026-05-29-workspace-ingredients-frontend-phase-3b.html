Implementation Plan: Workspace Ingredients Frontend Phase 3B

Approval required before implementation

Task Summary

Backend Phase 3A is deployed and exposes the compatibility API for workspace ingredient membership: GET /api/workspace-ingredients, POST/PATCH/DELETE /api/workspace-ingredients, GET /api/ingredients/search, and compatibility auto-linking on price and recipe ingredient writes.

Phase 3B should migrate the web frontend to this contract without breaking the current production workflows. The primary goal is to make the Ingredients page a workspace working-set screen and to move price and recipe pickers from the global dictionary to the active workspace ingredient set.

Current Behavior Confirmed From Code

Web Frontend

  • src/utils/fetcher.ts sends JWT auth but does not send X-Workspace-ID.
  • src/pages/ingredients.tsx reads /api/ingredients and displays the global dictionary.
  • src/pages/prices.tsx reads /api/ingredients for the price picker and posts to /api/prices.
  • src/pages/recipes.tsx, CreateRecipeModal, and EditRecipeModal use global ingredients for recipe ingredient writes.
  • fetcher.ts builds default headers, then spreads options; caller-provided options.headers can replace default auth/content headers.
  • FetchError currently preserves field, value, and existing_id, but not workspace_linked or workspace_ingredient metadata.
  • There is no current workspace selector or workspace persistence in the web auth context.

Mobile App

  • BatchVault/APIService.swift sends JWT auth but does not send X-Workspace-ID.
  • The current Swift client mostly reads recipes, products, orders, clients, dashboard, and profit data.
  • No active mobile write path for prices, ingredients, or adding recipe ingredients was found in APIService.swift.
  • Mobile still depends on backend personal-workspace fallback until it gets workspace selection.

Desired Behavior

  • Keep GET /api/ingredients as global dictionary compatibility; do not use it as the default web working list.
  • Use GET /api/workspace-ingredients for the Ingredients page, price picker, recipe create/edit pickers, and ingredient filters tied to workspace data.
  • Add a global search/add flow so a user can add an existing global ingredient to the workspace without seeing technical ids.
  • Keep the current price and recipe writes working; backend auto-link remains a fallback, not the primary UX.
  • Introduce a web workspace context that calls GET /api/workspaces and sends X-Workspace-ID when a user selects a non-default workspace.
  • Defer strict backend non-member rejection until web and mobile clients both use scoped pickers.

Recommended Scope Split

  • Phase 3B web PR: web workspace context, scoped ingredient working set, global search/add, picker migration, visual QA.
  • Phase 3C mobile PR: Swift workspace model/context/header, cache invalidation, and parity for any ingredient/price workflow the mobile app exposes.
  • Later backend tightening: switch write paths from compatibility auto-link to strict non-member rejection only after both clients are scoped.

Implementation Steps

  1. Add typed API models for workspaces and workspace ingredients.
  2. Add workspace provider or auth-adjacent state: fetch workspaces after login, choose default/current workspace, persist selected workspace in localStorage under a user-scoped key, validate the stored id against GET /api/workspaces, and clear it on logout. During bootstrap, do not send the persisted X-Workspace-ID until that id has been validated; otherwise the current global 403 handler can treat a stale workspace id as an auth failure and log the user out.
  3. Teach fetcher to send X-Workspace-ID for authenticated calls when a selected workspace exists. Header composition must merge Content-Type, Authorization, X-Workspace-ID, and caller headers instead of allowing options.headers to replace defaults. Gradually remove manual Authorization headers from pages where the shared fetcher can own them.
  4. Use tuple SWR keys for workspace-scoped reads: [endpoint, selectedWorkspaceId], handled by a wrapper fetcher that passes only the endpoint to the shared fetcher. Bootstrap workspace discovery, auth, and other non-workspace endpoints stay on ordinary string keys and must not send a persisted workspace header before validation. This makes cache bleed between workspaces impossible by construction instead of relying on a manually maintained global invalidation list.
  5. Build the Ingredients working-set screen on /api/workspace-ingredients with type filters, latest price signal, deactivate action, and empty state.
  6. Add global search/add flow using /api/ingredients/search and POST /api/workspace-ingredients.
  7. Extend FetchError and frontend API types to preserve workspace_linked, workspace_ingredient_id, and any returned workspace_ingredient metadata. Keep create-new ingredient flow on POST /api/ingredients; treat 409 with workspace_linked as a successful workspace-link outcome.
  8. Move price filters and Add Price picker to workspace ingredient options.
  9. Move recipe create/edit ingredient pickers to workspace ingredient options, while preserving already-used inactive ingredients in edit views so existing recipes remain readable and editable after a membership is deactivated.
  10. Run desktop and mobile browser QA, including workspace switching and ingredient add/deactivate flows.

Mobile Phase 3C Notes

  • Update APIService.makeRequest to send X-Workspace-ID after a workspace is selected.
  • Invalidate cached clients/orders/products/recipes/dashboard/profit when workspace changes.
  • Because this Windows workspace cannot run Xcode builds, final mobile verification must happen on macOS/Xcode or Xcode Cloud.

Manual QA Checklist

  • Log in and verify default workspace data appears without manual workspace selection.
  • Switch workspace and verify recipes, prices, products, clients, orders, and dashboard revalidate.
  • Open Ingredients and confirm only active workspace ingredients are listed.
  • Search global dictionary for an ingredient not in the workspace and add it.
  • Create a brand-new ingredient and confirm it appears in the workspace list.
  • Create a price using a workspace ingredient and confirm price list refreshes.
  • Create/edit a recipe using workspace ingredients and confirm cost lookup still works.
  • Deactivate a workspace ingredient and confirm historical prices/recipes still display where expected.
  • Edit a recipe that already uses a now-inactive workspace ingredient and confirm the ingredient remains visible in the recipe composition instead of disappearing from the edit surface.
  • Log out, log in as a different user in the same browser, and confirm stale selected workspace id is cleared or rejected after GET /api/workspaces.

Risks and Edge Cases

  • Cache bleed: workspace-scoped SWR reads must use tuple keys that include the selected workspace id. Reusing string-only keys for scoped data can show data from the previous workspace after switching.
  • Picker mismatch: price and recipe pages must not use global dictionary options after the scoped working set is introduced.
  • Header loss: existing callers pass custom options.headers; fetcher changes must merge headers so auth and workspace context are not dropped.
  • Stale selected workspace: selected workspace persistence must be user-scoped and validated after workspace fetch, otherwise another browser user can inherit an invalid workspace id. The provider must not send an unvalidated persisted id, because fetcher currently logs out on any 403.
  • 403 semantics: if implementation needs to distinguish workspace-forbidden from auth-forbidden, change fetcher deliberately rather than accidentally weakening auth logout behavior.
  • Mobile lag: backend strict mode must wait until mobile also sends workspace context.
  • Empty workspace: new workspace with no ingredients needs a useful add/search empty state, not a dead table.
  • 409 semantics: existing ingredient creation now returns conflict plus workspace link metadata; the UI should treat that as a recoverable/successful add-to-workspace path.
  • Inactive used ingredients: hiding inactive workspace ingredients from picker options is fine, but already-used recipe ingredients must still render and remain editable/removable.

Rollback Plan

  • Backend Phase 3A remains compatible, so the web frontend can temporarily fall back to GET /api/ingredients and auto-link writes.
  • If workspace switching causes cache bleed, hide selector and keep personal workspace fallback while preserving scoped ingredients page work.
  • Do not request backend strict mode until web and mobile parity are both verified.

Open Questions

  • Workspace selector placement: resolved for Phase 3B: place a compact selector near account/workspace identity, not in the main navigation list. If the user has only one workspace, show readonly identity or suppress dropdown affordance.
  • Deactivate visibility: resolved for Phase 3B: hide inactive workspace ingredients from the default working-set list and add/picker flows, while preserving already-used inactive ingredients as historical references in recipes and price history.
  • Latest price UI: resolved for Phase 3B: show missing/latest price signal on the Ingredients page only. Do not add price chips to compact recipe or price pickers in this phase.
  • SWR strategy: resolved for Phase 3B: use tuple keys for workspace-scoped reads with a wrapper fetcher. Keep bootstrap discovery and auth endpoints on string keys.
  • Mobile timing: resolved for Phase 3B: mobile workspace header lands after web 3B and before backend strict mode.

Approval Gate

Implementation must not start until this plan is explicitly approved. Web implementation should happen on codex/workspace-ingredients-frontend-plan or a fresh branch created from it. Mobile changes should be planned and implemented separately in Jerky-Vault-mob.
