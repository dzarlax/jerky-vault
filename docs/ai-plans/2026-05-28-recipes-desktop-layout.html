Implementation Plan: Recipes Desktop Layout

Planning artifact for improving the BatchVault recipes screen below the filter area while preserving a stable, work-focused interface.

Approval required before implementation

Task Summary

Redesign the desktop recipes screen so it is easier to scan and operate during production work. The target is the area below the page header and filters, with optional light cleanup of the filter toolbar if needed for the chosen layout.

The user explicitly does not want a masonry-style layout. Equal card heights within a grid row are acceptable and may remain, as long as the content composition is more useful.

Current Behavior

  • src/pages/recipes.tsx renders a page header, two SelectDropdown filters, then a card grid.
  • src/styles/components.css defines the base recipe card and recipe grid styles.
  • src/styles/batchvault-adapter.css adds the current BatchVault visual overrides for products and recipes.
  • At a 1440px desktop viewport, the content area is roughly 1100px wide after the sidebar, and the recipe grid currently resolves to three equal columns.
  • The current card body repeats large ingredient mini-cards. This consumes vertical space and makes short recipes look sparse when sharing a row with a longer recipe.

Design Constraints

  • No masonry layout and no staggered column heights.
  • Keep the screen utilitarian and dense enough for repeated operational use.
  • Keep existing data model and API behavior. This is a layout and presentation pass, not a recipes data rewrite.
  • Keep light and dark theme support.
  • Preserve mobile behavior, or intentionally scope mobile changes as follow-up if the implementation only targets desktop.

Recommendation

Implement Mockup B first

Mockup B is now the preferred direction. It is the most practical layout for an operator who is not just browsing recipes, but selecting one, checking its ingredients and costs, and then calculating or editing it.

The implementation should still be conservative: keep the existing API calls, filters, modals, and action semantics. The layout change should introduce local selected-recipe state and a desktop split view, while using a simpler stacked list/detail pattern on mobile.

Explicit non-goal:

No masonry-like uneven card layout. The recommended design replaces the card grid on desktop with a stable master-detail workbench.

Desired Behavior

  • Desktop users see a recipe list and a persistent details panel side by side.
  • Selecting a recipe updates the details panel without opening a modal or navigating away.
  • The details panel shows recipe name, total cost, ingredient count, missing-cost state, compact ingredient rows, and primary actions.
  • The filter area becomes a compact control strip instead of a large card: text search by recipe name, ingredient dropdown, result count, and clear/reset only when active.
  • The first available recipe is selected by default when recipes load, unless a filter leaves no results.
  • Existing actions remain available: create recipe, calculate, edit, delete/clone through edit modal.
  • Filtering by recipe or ingredient still works exactly as it does now.

Mobile and Empty States

The master-detail layout must not become a cramped two-column screen on mobile. Below the desktop breakpoint, the UI should collapse into a single-column recipe list. The selected recipe detail can appear directly below the selected row, or as a clearly separated detail section after the list.

Required state handling

No recipes yet Show the existing empty recipe state with a create action. Do not render an empty details panel.
No filter results Keep filters visible, show a no-results message, and offer clear filters. Do not preserve a stale selected recipe.
Loading/error Skeleton or loading state should cover both list and detail areas. API errors should use the existing error/notification pattern.

Add Recipe Modal: Current Problem

The current add-recipe modal is a narrow linear form: recipe name, ingredient, quantity, unit, add button, then an empty or populated ingredient list. It works technically, but it gives little context while building the recipe and uses disruptive validation alerts.

  • Adding several ingredients requires too much vertical scanning.
  • The ingredient list is not visually connected to the builder controls.
  • Validation should be inline, not browser alerts.
  • The save action should clearly communicate when the recipe is ready to create.
  • Mobile must remain a single-column flow with a useful empty state.

Files Likely to Change

  • src/pages/recipes.tsx - replace the desktop grid rendering with recipe-list plus selected-detail rendering, add selected recipe state, add text search/filter derivation, and add derived metadata such as ingredient count and missing-cost count.
  • src/components/modal/Recipe/CreateRecipeModal.tsx - redesign the add-recipe form, remove alert-based validation, add inline errors, keep the existing onCreateRecipe(name, ingredients) contract.
  • src/styles/batchvault-adapter.css - add desktop workbench, list, detail panel, mobile collapse, and empty-state layout rules in the adapter layer.
  • src/styles/components.css - only if an older base rule blocks the adapter from cleanly controlling the recipe layout.
  • locales/en/common.json, locales/ru/common.json, locales/rs/common.json - likely for new labels such as "search recipes", "missing costs", builder helper copy, and inline validation copy.

Implementation Steps

  1. Keep the existing SWR calls, filter state, modal state, and auth behavior unchanged.
  2. Add local selectedRecipeId state and derive selectedRecipe from the filtered recipe list.
  3. Replace the recipe-name dropdown filter with a text search input for recipe names, while keeping the ingredient dropdown for structured filtering.
  4. Show a compact result summary near the controls, and show the clear/reset control only when search text or ingredient filter is active.
  5. When recipes load or filters change, select the first available recipe if the current selection is no longer visible.
  6. Render a desktop workbench below filters: left list of recipes, right detail panel for the selected recipe.
  7. Render no details panel when the list is empty; show the proper empty or no-results state instead.
  8. Use compact ingredient table rows in the details panel, with clear handling for N/A costs.
  9. Make action buttons easier to recognize, likely icon plus text on desktop and compact buttons on mobile.
  10. Add responsive rules so mobile becomes a single-column list/detail flow and never a squeezed two-column workbench.
  11. Check light and dark themes.

UX Impact

  • No backend, database, auth, permission, deployment, or API contract changes are expected.
  • The main workflow stays the same: users browse recipes, filter, create, calculate, and edit.
  • The browsing workflow changes from "scan cards" to "select from a list and inspect details". This should reduce visual noise on desktop.
  • Mobile must remain a simple one-column flow and should not expose a desktop-like split pane.

Test Plan

  • Run npm run lint.
  • Run npm run build or npm run build:no-ssg if normal build is blocked by environment validation.
  • Open http://localhost:3000/recipes at desktop width, verify recipe cards, filters, calculate, and edit actions.
  • Check mobile width below 992px to confirm the sidebar and cards remain usable.
  • Check dark mode because recipe cards have theme-specific styles.

Manual QA Checklist

  • Recipe count still matches the loaded list.
  • Searching by recipe name and filtering by ingredient still changes the visible recipes.
  • Clear filters still resets the list.
  • The clear/reset control is not shown when no filters are active.
  • The selected recipe updates when a recipe row is clicked.
  • The selected recipe resets safely when filters hide the previous selection.
  • No stale recipe details are shown when filters return zero results.
  • The "no recipes yet" empty state does not show an empty workbench shell.
  • Mobile width shows a single-column flow, not a squeezed list/detail split.
  • Create recipe modal still opens and saves.
  • Edit modal still opens for the intended recipe.
  • Calculator still receives the intended recipe.
  • Cards do not overflow with long Cyrillic, English, or Serbian ingredient names.
  • Amounts and currency values remain legible when they are N/A.

Risks and Edge Cases

  • Selection state can become stale after filtering, deleting, or cloning a recipe unless it is explicitly reconciled with the visible recipe list.
  • Mobile can become worse than the current screen if the split-pane design is merely squeezed instead of collapsed.
  • Empty states can look broken if the detail panel renders without a selected recipe.
  • Missing-cost metadata may require careful checks because the current data can contain calculated_cost, N/A, or absent values.
  • Existing CSS specificity in components.css may conflict with adapter rules.
  • Translated labels can be longer than English and may need compact wording.

Rollback Plan

Revert the recipe markup and selection-state changes in src/pages/recipes.tsx and remove the matching recipe workbench rules from src/styles/batchvault-adapter.css. Because this plan should not alter API calls or data writes, rollback should be limited to frontend presentation files.

Open Questions

  • Should recipe-name filtering become text search, or should the existing recipe dropdown stay available as an advanced exact selector?
  • Should missing ingredient prices be visually emphasized as an operational warning, or stay muted to avoid noise?
  • On mobile, should tapping a recipe row expand details inline, or scroll to a single details section below the list?
  • Should desktop action buttons use text labels ("Calculate", "Edit") or remain icon-only with clearer placement?

Approval Gate

Implementation must not start until the user explicitly approves this updated direction. Recommended approval target: Mockup B, with a desktop master-detail workbench, a single-column mobile fallback, and explicit empty/no-results handling.

Actual Implementation

  • Implemented the Mockup B direction in src/pages/recipes.tsx: desktop recipe list plus selected detail panel.
  • Changed recipe filtering from recipe dropdown to text search by recipe name, while keeping the ingredient dropdown filter.
  • Added selected-recipe reconciliation so filtering selects the first visible recipe and no-results states do not show stale details.
  • Added mobile inline details under the selected recipe row and hid the desktop detail panel below the tablet breakpoint.
  • Added soft missing-cost handling: zero, absent, or invalid cost values render as N/A and contribute to the missing-cost count.
  • Added recipe workbench styling in src/styles/batchvault-adapter.css, including dark-theme placeholder handling and mobile page-header offset to avoid the hamburger button overlapping the title.
  • Added translation keys for search, missing costs, and empty ingredient detail text in all three locales.
  • Implemented Add Recipe Mockup A as a builder modal in src/components/modal/Recipe/CreateRecipeModal.tsx: desktop two-column builder plus composition panel, single-column mobile fallback, inline validation, disabled save until ready, and no alert-based validation.
  • Added count pluralization in src/utils/pluralize.ts so Russian recipe and ingredient counters render as natural text instead of lowercased dictionary labels.
  • Adjusted the Add Recipe builder row for Russian desktop copy: the add action now uses shorter text, sits below the ingredient inputs, and the select/input controls keep a consistent height and baseline.

Known Limitations

  • The in-app browser's virtual clipboard was unavailable, so automated search input used key presses instead of direct field fill. The user-facing behavior was still verified.
  • The backend currently appears to represent some missing cost values as zero; the frontend now treats values less than or equal to zero as missing for recipe display.
