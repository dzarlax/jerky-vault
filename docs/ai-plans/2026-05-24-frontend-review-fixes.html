Task Summary

Fix the concrete frontend issues found during review after backend-side security and API changes: dashboard order action crashes, profile password-change response handling, password validation copy, Windows build script compatibility, and API base URL documentation/config consistency.

Current Behavior

P0 Dashboard order actions call mutateDashboardStats(), but the dashboard SWR hook currently exposes the mutate function as mutate. This will throw at runtime after order update, status change, or delete from src/pages/index.tsx.

P1 src/pages/profile.tsx treats password-change success as response.success, while the backend returns { "message": "Password changed successfully" }.

P2 Profile validation uses t('passwordTooShort'), but locale files contain passwordMinLength. The signup page already uses passwordMinLength.

P2 npm run build:no-ssg fails on Windows because package.json uses POSIX-style inline environment variables.

P3 .env.example documents NEXT_PUBLIC_API_URL=http://localhost:8080/api, but fetcher appends endpoints such as /api/auth/login. This can produce /api/api/... if copied literally.

Desired Behavior

  • Dashboard order update, status change, and delete refresh both the order list and dashboard stats without runtime errors.
  • Profile password change shows success when the backend returns its current successful message response.
  • All frontend password-minimum validation and locale copy consistently use the backend policy of 8 characters.
  • Build commands are runnable from this Windows workspace and remain suitable for Docker/Linux use.
  • API URL examples make it clear whether the variable is the API origin or the full /api base path.

Assumptions and Unknowns

  • Backend password policy is intentionally 8 characters, based on inspected ../jerky-vault-back/controllers/auth.go and ../jerky-vault-back/controllers/profile.go.
  • The frontend should keep using the shared fetcher contract where endpoints include their own /api/... prefix.
  • Deployment is a real VPS-backed service, so build script changes should be conservative and avoid breaking Docker workflows.
  • Existing TypeScript errors outside this fix set are not automatically in scope unless they block the targeted changes or verification.

Files Likely to Change

  • src/pages/index.tsx - rename the dashboard SWR mutate binding to mutateDashboardStats or update the call sites to the existing mutate.
  • src/pages/profile.tsx - accept backend success via response.message or simply treat a resolved fetcher call as success; use the existing passwordMinLength translation key.
  • locales/en/common.json, locales/ru/common.json, locales/rs/common.json - only if a clearer dedicated passwordTooShort key is preferred over reusing passwordMinLength.
  • package.json - make build scripts cross-platform, likely with cross-env or a small Node script. Adding a dependency should be weighed against keeping scripts shell-specific.
  • package-lock.json - if cross-env is added.
  • .env.example, README.md, DOCKER.md - align examples with the actual base URL convention.
  • docs/ai-plans/2026-05-24-frontend-review-fixes.html - update after implementation with actual changes, checks, limitations, and follow-ups.

Risks and Edge Cases

  • Adding cross-env modifies dependency metadata. If dependency churn is undesirable, use a small Node wrapper instead.
  • Profile password-change QA can lock a test account into a new password. Use a disposable account or immediately restore the old password.
  • Dashboard delete QA must avoid real production data unless the user explicitly confirms it is safe.
  • Fixing only the reviewed issues leaves existing broader TypeScript debt in place; the plan should clearly report that if tsc still fails.
  • Changing API URL docs must match the actual deploy environment; do not overwrite private .env values unless explicitly requested.
