Implementation Plan: Frontend Price Decimal and RSD Cleanup

Approval required before implementation

Task Summary

Continue the web frontend branch codex/fix-currency-symbols. The branch already replaces hardcoded ruble symbols in price/product/order UI with the localized currency value, which is currently RSD. This plan adds the related price-entry fixes needed before backend decimal price quantities ship: preserve decimal quantities, align count units, and verify price display remains correct in RSD.

Current Behavior From Code Inspection

  • locales/en/common.json, locales/ru/common.json, and locales/rs/common.json already define "currency": "RSD".
  • The current branch has uncommitted RSD cleanup in src/components/modal/Prices/AddPriceModal.tsx, src/components/modal/Products/ProductModal.tsx, and src/pages/orders.tsx.
  • AddPriceModal accepts quantity as a string, uses type="number" with step="0.01", and validates with parseFloat.
  • src/pages/prices.tsx currently builds the create-price payload with quantity: parseInt(priceData.quantity, 10), which truncates decimal inputs like 2.5.
  • src/types/api.ts already models Price.quantity as number, so the response type can represent decimals.
  • src/utils/ingredientTypes.ts centralizes units by ingredient type. It currently maps packing to pieces, while the backend calculation path supports pcs.
  • The prices table displays quantity directly as {price.quantity} and unit via {t(price.unit)}.

Desired Behavior

  • All visible money prefixes/suffixes in touched price, product, and order flows use t('currency'), not hardcoded ₽.
  • Adding a price from the web UI preserves decimal quantity in the payload sent to POST /api/prices.
  • Decimal inputs accept normal browser decimal entry; comma handling is optional for this web pass unless existing controls allow it cleanly.
  • Count/packing units use a backend-compatible canonical value. Recommendation: send pcs and translate it as pieces/штуки/komadi in locales.
  • Existing price history and ingredient latest-price displays continue to show numeric quantities without forcing integer formatting.
  • No backend schema, API, mobile, or deployment changes in this frontend branch.

Implementation Steps

  1. Keep work on branch codex/fix-currency-symbols and preserve the existing uncommitted RSD edits.
  2. Add a small local helper in prices.tsx or near the submit handler to normalize numeric strings with trim() and decimal parsing.
  3. Change request construction from parseInt(priceData.quantity, 10) to a decimal value. Do not silently submit NaN.
  4. If approved, switch packing units from pieces to pcs in ingredientTypes.ts and add locale labels for pcs.
  5. Search for remaining hardcoded ₽ and any price-creation parseInt(...quantity...) paths.
  6. Update this plan after implementation with exact changes and checks run.

Risks and Edge Cases

  • Frontend decimal submission depends on backend decimal support; until backend is deployed, decimal values may be rejected or coerced server-side.
  • Changing pieces to pcs can affect existing untranslated display if locale keys are incomplete.
  • Browser type="number" behavior is locale-sensitive; comma decimal entry may not work consistently without changing input handling more broadly.
  • The branch has unrelated untracked local files in the repo. Stage only intended frontend files and this plan.

Rollback Plan

  • RSD display changes can be reverted independently by restoring hardcoded symbols, though this is not recommended because locales already define RSD.
  • If backend decimal support is delayed, keep UI decimal-capable but do not rely on decimal saves in QA, or revert only the parseInt change temporarily.
  • If unit canonicalization causes display issues, revert pcs mapping while keeping decimal quantity preservation.
