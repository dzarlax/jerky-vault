Implementation Plan: Products Screen Redesign

Created 2026-05-30 for branch codex/products-screen-redesign.

Task Summary

Redesign the Products screen around image-free detail cards and make product packaging a first-class page control via package chips above the card list.

The approved mockup direction is Detail Cards + Package Chips Above Cards. Product images should not drive the layout because most users are unlikely to upload them.

Current Behavior

  • src/pages/products.tsx fetches products, recipes, and packages with workspace-aware SWR keys.
  • The page currently renders a header, three dropdown filters, and a .products-grid of ProductCard components.
  • src/components/ProductCard.tsx reserves a large top area for product.image or product.image_url, with a box icon fallback when no image exists.
  • src/components/modal/Products/ProductModal.tsx already lets users pick a package and open PackageModal from inside the product modal.
  • src/components/modal/Products/PackageModal.tsx creates packages by name only, even though ProductPackage in src/types/api.ts includes weight.
  • BatchVault UI conventions say dense operational screens should use stable compact layouts, translated labels, SelectDropdown, and put product-level visual decisions in src/styles/batchvault-adapter.css.

Desired Behavior

Products Page

  • Keep the page as a catalog, not a pure table.
  • Remove the image-first card layout.
  • Add a package chip strip above the products, including an All packages state and an add-package icon action.
  • Keep recipe and product search/filter controls compact above or beside the chip strip.
  • Show each card with product name, package chip, description, recipe summary, price, cost, profit, and margin.

Assumptions And Unknowns

  • Assumption: this frontend-only pass should not change backend package APIs or database schema.
  • Assumption: package creation remains name-only in this phase; package weight should not be introduced in the UI until the backend contract is verified.
  • Assumption: product images can remain in the API type and modal field for backward compatibility, but cards should not reserve image space.
  • Unknown: whether users need package edit/delete on the Products page. This plan includes create package only, matching current behavior.
  • Unknown: whether package names may be long enough to require truncation; implementation should handle this defensively.

Files Likely To Change

  • src/pages/products.tsx - add package-chip state/handlers, route package creation from the page, adjust filters, and pass richer display data into cards.
  • src/components/ProductCard.tsx - replace image-first card with image-free detail card layout and recipe/package summaries.
  • src/components/modal/Products/ProductModal.tsx - keep package selection and nested package creation working; remove image field from the primary visual hierarchy if needed.
  • src/components/modal/Products/PackageModal.tsx - make it usable from both page chip strip and product modal without duplicating SWR refresh behavior.
  • src/styles/batchvault-adapter.css - add BatchVault-specific product card, package chip strip, and responsive layout styling.
  • locales/en/common.json, locales/ru/common.json, locales/rs/common.json - add any new labels for package chip actions and compact card metadata.
  • src/components/skeletons/ProductCardSkeleton.tsx - update loading skeleton to match the image-free card shape.

Proposed Implementation Steps

  1. Confirm branch and working tree state before production edits.
  2. Extract package chip UI into the Products page or a small local component if the page becomes hard to read.
  3. Update package filtering so clicking a chip sets the selected package and the clear action resets recipe/product/package filters.
  4. Wire the add-package chip to open PackageModal from the Products page, while preserving nested package creation inside ProductModal.
  5. Redesign ProductCard to remove image space and show compact operational metadata.
  6. Update the product skeleton to the same image-free structure to avoid loading jumps.
  7. Add responsive styles in batchvault-adapter.css: horizontal chip scroll on mobile, one-column cards on narrow viewports, stable metric grid.
  8. Add or reuse translation keys for package chip labels and card metadata in all three locale files.
  9. Run lint/build checks and fix TypeScript or lint failures caused by the refactor.
  10. Update this plan after implementation with actual changes, checks, known limitations, and follow-up recommendations.

UX Impact

  • Products become easier to scan when most products have no images.
  • Packaging becomes visible as a primary organizing control instead of being buried in a dropdown or modal.
  • The page remains useful for both browsing and repeated operational maintenance.
  • No auth, permission, deployment, migration, or API contract change is planned in this phase.

Test Plan

  • Run npm run lint. Expected: no new lint errors from touched files.
  • Run npm run build:no-ssg. Expected: Next.js build completes with the project's existing SSG bypass behavior.
  • Use the existing dev compose stack for browser QA: docker compose -f docker-compose.dev.yml ps, then inspect http://127.0.0.1:3000/products in desktop and mobile widths.
  • Verify package chip filtering with mock or live data: all packages, individual package, recipe filter plus package filter, product filter plus package filter, and clear filters.
  • Verify creating a package from the chip strip updates package options and can be selected without full page reload.
  • Verify creating a package from inside ProductModal still selects the new package for the product being edited.

Manual QA Checklist

  • Products page renders without product images and without a large empty placeholder area.
  • Long product names, long package names, and long descriptions do not overlap or stretch cards awkwardly.
  • Package chips are keyboard and pointer usable, with selected state visible in light and dark themes.
  • Add Product remains prominent in the header.
  • Add Package is discoverable near the package chip strip.
  • Cards remain readable on mobile, tablet, and desktop widths.
  • ProductModal remains scrollable and footer actions remain reachable on mobile.
  • Empty, loading, and error states still match the new card/list structure.

Risks And Edge Cases

  • Duplicating package creation in both page and product modal can cause stale SWR data if mutations are not coordinated.
  • Package chip strip can become crowded if a workspace has many packages; mobile should use horizontal scrolling instead of wrapping into a tall block.
  • Removing image prominence could surprise existing users who already added images, so the image URL should not be deleted from edit data in this phase.
  • Translation files currently contain duplicate failedToDeleteProduct keys; avoid broad locale cleanup unless it blocks this work.
  • The backend package model includes weight, but current package modal creates only name; avoid exposing weight until backend behavior is confirmed.

Rollback Plan

Rollback is limited to frontend files. Revert the branch changes to src/pages/products.tsx, product modal/package modal components, product card/skeleton components, locale keys, and src/styles/batchvault-adapter.css. No database or backend rollback is expected because this plan does not change backend contracts.

Open Questions

  • Should package chips show counts, such as 100g (6), or should that wait until after the first implementation pass?
  • Should the image URL field remain visible in the product modal, move to an optional advanced area, or be removed from the modal while preserving stored values?
  • Should package edit/delete be added later as a separate package-management pass?

Implementation Notes

Known Limitations And Follow-up

  • Package edit/delete remains out of scope. The page supports package creation and filtering only.
  • Package weight is still not exposed because this pass intentionally avoided backend contract changes.
  • Products now resolve recipe labels from the separately loaded recipes list when the product option carries only recipe_id or a zero-value embedded recipe object from the backend.
  • The image URL field remains in the product modal for backward compatibility, but card layout no longer depends on images.
